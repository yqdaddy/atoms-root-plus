## 1. 背景与目标

用户反馈当前"只生成单文件 HTML，不是真实可用的应用"。本次升级将按工程化思维生成真实项目结构，让用户感知到"这是一次真正的开发过程"而非"一个简单 demo"。核心升级包括：（1）新增提示词工程优化阶段，将模糊需求转化为结构化需求文档；（2）从单文件 HTML 升级为标准工程化目录结构；（3）支持多文件独立生成与增量修改；（4）完善版本历史与回滚能力。

成功标准：用户输入模糊需求后，系统能自动优化为结构化需求文档，经用户确认后生成包含至少 3 个文件的真实项目结构，且单文件增量修改不破坏其他文件。

## 2. 用户故事

优先级沿用第 3 章定义：P0 缺失则核心功能不成立；P1 显著提升体验；P2 锦上添花。

### P0（核心功能底线）

- **US-101**（P0）作为用户，我想要在提交模糊需求后看到 AI 优化后的结构化需求文档，以便确认需求理解正确后再开始生成。
- **US-102**（P0）作为用户，我想要在结构化需求中看到技术方案、边界条件、交互流程等细节补充，以便理解 AI 的实现思路。
- **US-103**（P0）作为用户，我想要在需求文档中修改或补充内容后再批准生成，以便对需求有最终控制权。
- **US-104**（P0）作为用户，我想要生成的项目包含标准目录结构（如 `src/components/`、`src/styles/`），以便感知这是"真实项目"而非单文件 demo。
- **US-105**（P0）作为用户，我想要在文件面板中看到多个独立文件并逐个生成，以便了解项目的组成结构。
- **US-106**（P0）作为用户，我想要发起"修改某个组件"的需求时只重新生成该文件，以便迭代修改不影响其他已完成的部分。
- **US-107**（P0）作为用户，我想要在沙箱预览中看到多文件组装后的完整应用效果，以便确认各文件正确协作。

### P1（显著提升体验）

- **US-108**（P1）作为用户，我想要在需求文档确认前看到预设的疑问与建议，以便补充我未提及的关键信息。
- **US-109**（P1）作为用户，我想要查看单个文件的独立代码内容，以便学习或检查某个组件的实现。
- **US-110**（P1）作为用户，我想要下载整个项目为 zip 包，以便在其他开发环境中继续使用。
- **US-111**（P1）作为用户，我想要查看单个文件的版本历史，以便追溯某次修改的具体内容。
- **US-112**（P1）作为用户，我想要回滚某个文件到历史版本，以便撤销对特定文件的修改。

### P2（锦上添花）

- **US-113**（P2）作为进阶用户，我想要在需求文档中手动指定技术栈偏好（如 Tailwind vs 原生 CSS），以便控制实现风格。
- **US-114**（P2）作为用户，我想要对比两个版本文件的差异，以便了解具体修改了什么。

## 4. 验收标准

### P0 用户故事

**US-101 验收标准**
1. 输入"做一个待办清单"并提交后，系统不立即开始生成代码，而是先输出结构化需求文档。
2. 需求文档包含：应用名称、功能清单（带优先级）、技术方案概述、关键边界条件、主要交互流程。
3. 从提交需求到需求文档开始流式输出的时间不超过 5 秒（演示模式立即出现）。

**US-102 验收标准**
1. 需求文档中"技术方案概述"至少包含：主要技术选型说明、组件拆分思路、数据存储方案。
2. 需求文档中"边界条件"至少包含 3 条：如空数据处理、错误状态、极端情况。
3. 需求文档中"交互流程"以步骤序列描述主要用户操作路径，至少 5 步。

**US-103 验收标准**
1. 需求文档以可交互形式展示（非纯文本），用户可点击编辑任一字段。
2. 用户编辑内容后点击"批准并生成"，系统按修改后的需求开始生成。
3. 用户可点击"取消"放弃本次需求，回到输入状态，不产生任何文件变更。

**US-104 验收标准**
1. 生成的项目文件树包含至少 3 个目录层级（如 `/src/components/`）。
2. 生成的项目文件树包含至少 4 个文件（入口文件 + 至少 3 个组件/样式/工具文件）。
3. 文件路径符合约定规范：入口为 `/index.html`，组件在 `/src/components/` 下，样式在 `/src/styles/` 下。

**US-105 验收标准**
1. 文件面板以树形结构展示所有文件，目录可折叠展开。
2. 生成过程中，当前正在生成的文件显示加载状态（图标旋转或进度指示）。
3. 已完成生成的文件显示完成状态（绿色勾选图标），未开始生成的文件显示待处理状态。

**US-106 验收标准**
1. 在已生成项目基础上输入"把 Header 组件的背景改成蓝色"，系统仅重新生成 `Header.jsx`（或对应文件）。
2. 其他文件（如 `App.jsx`、`main.css`）的时间戳不变，内容不变。
3. 修改完成后预览自动刷新，显示修改后的效果。

**US-107 验收标准**
1. 预览区正确渲染多文件组装后的应用，组件间引用（如 `import Header from './Header'`）生效。
2. 样式文件正确应用到组件（如 `main.css` 中的样式生效）。
3. 预览中交互功能正常（按钮可点击、表单可提交、动画可触发）。

### P1 用户故事

**US-108 验收标准**：需求文档中包含"需要确认的问题"区块，至少列出 2 个问题；包含"建议补充"区块，至少列出 1 条建议；用户可点击建议快速采纳。

**US-109 验收标准**：点击文件树中的任意文件，右侧代码面板显示该文件的完整代码；代码有语法高亮；提供一键复制按钮，点击后复制成功有提示。

**US-110 验收标准**：点击"导出项目"按钮，浏览器下载 zip 文件；解压后目录结构与在线一致；解压后入口文件 `index.html` 可直接在浏览器中打开运行。

**US-111 验收标准**：每个文件至少保留最近 10 个版本；版本列表显示生成时间与触发原因（如"初始生成""修改背景色"）；点击版本可查看该版本代码内容。

**US-112 验收标准**：选择某个历史版本点击"回滚"，该文件恢复为该版本内容；回滚后预览自动刷新显示回滚后效果；回滚操作本身创建新版本记录（可追溯回滚历史）。

### P2 用户故事

**US-113 验收标准**：设置中有"技术栈偏好"区块，可选择样式方案（Tailwind/原生 CSS/SCSS）；选择后新项目的需求文档中自动应用该偏好；用户可在单次需求中覆盖偏好设置。

**US-114 验收标准**：版本历史中可选择两个版本点击"对比"；显示新增/删除/修改行的差异高亮；可导出差异报告。

## 5. 工程化项目结构规范

### 5.1 标准目录结构

```
project/
├── index.html              # 入口 HTML（必须）
├── src/
│   ├── main.js             # 应用入口脚本
│   ├── App.jsx             # 根组件（如适用）
│   ├── components/
│   │   ├── Header.jsx      # 头部组件
│   │   ├── Footer.jsx      # 底部组件
│   │   └── [Feature].jsx   # 功能组件
│   ├── styles/
│   │   ├── main.css        # 主样式文件
│   │   └── variables.css   # CSS 变量（可选）
│   └── utils/
│       └── helpers.js      # 工具函数（可选）
└── package.json            # 项目元信息（可选，用于导出）
```

### 5.2 文件类型与用途

| 类型 | 扩展名 | 用途 | 是否必须 |
|---|---|---|---|
| 入口文件 | `.html` | 浏览器直接打开的入口，引入其他资源 | 是 |
| 组件文件 | `.jsx` / `.js` | 可复用的 UI 组件 | 视项目类型 |
| 样式文件 | `.css` | 样式定义，支持 CSS 变量 | 是 |
| 工具文件 | `.js` | 工具函数、数据处理 | 否 |
| 配置文件 | `.json` | 项目元信息、依赖声明 | 否 |

### 5.3 组装器行为约定

1. **入口组装**：`index.html` 作为沙箱入口，组装器注入必要的运行时脚本。
2. **引用解析**：组件间的 `import` 语句由组装器转换为沙箱可执行的形式。
3. **样式注入**：CSS 文件内容以 `<style>` 标签形式注入到 HTML。
4. **运行时兼容**：对于 JSX 件，组装器注入轻量运行时（如 htm + preact）或预编译为 JS。

## 6. 提示词工程优化阶段规范

### 6.1 需求文档结构

AI 输出的结构化需求文档包含以下区块：

| 区块 | 内容 | 格式 |
|---|---|---|
| 应用名称 | 用户需求中提取或推断的应用名 | 单行文本 |
| 应用类型 | 分类标签（如"工具类""展示类""数据类"） | 枚举 |
| 功能清单 | 按优先级排序的功能点列表 | 列表（id、名称、描述、优先级） |
| 技术方案 | 主要技术选型与架构思路 | 多段落文本 |
| 边界条件 | 异常处理、极端情况、限制说明 | 列表 |
| 交互流程 | 主要用户操作路径 | 步骤序列 |
| 待确认问题 | AI 认为需要用户确认的事项 | 列表（可采纳/忽略） |
| 建议补充 | AI 建议增加的功能或优化 | 列表（可采纳/忽略） |

### 6.2 用户交互流程

```
用户输入模糊需求
    ↓
AI 分析并输出结构化需求文档（流式）
    ↓
用户查看、编辑需求文档
    ↓
用户确认（批准）或取消
    ↓
[批准] → AI 开始按需求文档生成代码
[取消] → 回到输入状态，无变更
```

## 7. 多文件生成流程规范

### 7.1 生成阶段调整

原三阶段（分析 → 生成 → 审查）调整为：

| 阶段 | 内容 | 输出 |
|---|---|---|
| 需求优化 | 解析用户需求，输出结构化需求文档 | 需求文档 JSON |
| 规划 | 根据需求文档规划文件结构与组件拆分 | 文件清单、组件依赖图 |
| 生成 | 按规划逐文件生成代码 | 多文件代码 |
| 组装 | 将多文件合成为可预览的整体 | 组装后的 HTML |
| 审查 | 检查代码质量、功能完整性 | 审查报告、修复建议 |

### 7.2 文件生成顺序

1. 先生成入口文件（`index.html`）确定整体骨架
2. 按依赖顺序生成组件（被依赖的先生成）
3. 生成样式文件
4. 生成工具文件（如有）

### 7.3 增量修改策略

当用户发起修改请求时：

1. **意图识别**：判断修改目标文件（如"修改 Header 背景"目标为 Header 组件）
2. **上下文提取**：提取当前文件内容作为参考
3. **单文件重生成**：仅重新生成目标文件
4. **重新组装**：将修改后的文件重新组装预览

## 8. 非目标

以下内容明确不做，防止范围蔓延：

1. **真实后端服务**：生成物仍为纯前端应用，不生成 Node.js 后端、数据库连接等。
2. **真实构建工具链**：不生成需要 webpack/vite 构建的项目，组装器在运行时处理模块化。
3. **TypeScript 编译**：生成代码使用 JavaScript，不引入编译步骤。
4. **npm 依赖安装**：不生成需要 `npm install` 的项目，所有依赖通过 CDN 或内联引入。
5. **代码测试用例**：不生成单元测试或 E2E 测试代码。
6. **协作编辑**：不支持多人实时协作编辑同一文件。
7. **代码 Lint/Format**：不集成 ESLint/Prettier 等工具。
