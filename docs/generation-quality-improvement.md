# 代码生成质量改进方案

## 诊断结论

当前系统的主要问题：
1. **提示词过长且重复**（约 3000 tokens 基础开销）
2. **三阶段流水线缺乏闭环反馈**
3. **功能完整性未强制执行**
4. **审查失败后无自动修复循环**

## 改进方案

### 方案 A：提示词重构（短期，高收益）

**目标**：减少 50% token 消耗，提升模型对核心要求的注意力

**具体措施**：
1. **移除重复内容**
   - 功能完整性表格只在 Engineer prompt 中出现
   - Analyst 只负责需求澄清，不列具体功能模板

2. **结构化指令替代长表格**
   - 将表格转换为更简洁的检查清单
   - 使用模板变量而非完整示例

3. **核心要求前置**
   - 将"必须实现的功能"放在 prompt 开头
   - 减少示例长度，保留关键要点

**实施优先级**：🔴 P0

---

### 方案 B：自动修复循环（中期，高收益）

**目标**：审查失败时自动修复，减少用户干预

**具体措施**：
1. **增加修复循环阶段**
   ```
   Analyst → Engineer → Reviewer → (失败) → Fixer → Reviewer
   ```
   - 最多修复 2 次
   - Fixer 使用审查者的 `repairInstructions`

2. **审查者输出增强**
   - 输出具体的修复代码片段
   - 标注缺少的功能项

**实施优先级**：🟠 P1

---

### 方案 C：功能完整性强制执行（长期，根本解决）

**目标**：从代码层面验证功能完整性

**具体措施**：
1. **代码分析器**
   - 解析生成的 HTML/JS
   - 检查是否存在对应功能的代码（如事件绑定、DOM 元素）

2. **自动化测试**
   - 基于功能清单生成测试用例
   - 使用 Playwright 或 Puppeteer 验证

**实施优先级**：🟡 P2（需要大量工程投入）
