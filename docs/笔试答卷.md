## 一、实现思路与关键取舍

### 1.1 核心定位

对标 atoms.dev 的核心体验：**自然语言输入 → Agent 团队协作 → 可交互应用 → 沙箱预览 → 多轮迭代**。在 6-8 小时内聚焦主流程闭环，放弃复杂边缘功能。

### 1.2 技术栈选型

| 层 | 选型 | 取舍理由 |
|---|------|---------|
| 前端框架 | React 19 + Vite 8 + TypeScript 7（strict） | 现代工具链，类型安全，热更新快 |
| 样式 | Tailwind CSS 4 | 原子化，无需维护 CSS 文件，迭代效率高 |
| 状态管理 | Zustand 5 + persist | 比 Redux 轻量，天然支持 localStorage 持久化 |
| 后端框架 | Hono + @hono/node-server | 极简（~50 行路由），TypeScript 原生，无 Express 历史 |
| 数据库 | better-sqlite3（WAL） | 零运维，单文件，WAL 模式支持并发读 |
| 沙箱 | iframe sandbox + srcdoc | 浏览器原生隔离，postMessage 校验来源 |
| 部署 | GitHub Actions + rsync + pm2 | 推送即部署，pm2 管理进程与内存限制 |

**关键取舍**：
- **localStorage 优先 + 服务端同步**：游客模式零门槛，登录后自动合并到云端，符合 PRD "评委可能无 API Key" 的场景
- **单文件 HTML 应用**：生成产物简单可控，适合 Demo 范围；多文件工程需要脚手架系统，超出 8h 范围
- **后端代理 LLM 密钥**：前端永远不接触密钥，安全性高；降级到 demoEngine 保证无 Key 可用

### 1.4 三阶段 AI 流水线

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   分析阶段    │───►│   批准阶段    │───►│   生成阶段    │
│  (analyzing) │    │ (waiting)    │    │ (generating) │
└──────────────┘    └──────────────┘    └──────────────┘
       │                   │                   │
       ▼                   ▼                   ▼
  • 解析用户需求      • 展示功能清单      • 生成 HTML 代码
  • 生成功能清单      • 用户确认/取消     • 内联样式脚本
  • 输出 JSON 结构    • sessionId 关联    • CSP 白名单限制
                                           │
                                           ▼
                                    ┌──────────────┐
                                    │   审查阶段    │
                                    │ (reviewing)  │
                                    └──────────────┘
                                           │
                                           ▼
                                    • 检查代码质量
                                    • 验证可渲染性
                                    • 输出问题清单
```

**设计意图**：human-in-the-loop 防止"用户说 A、模型理解成 B、浪费 5 分钟生成错误产物"。批准成本 < 10 秒，避免了更高的重试成本。

### 1.5 沙箱安全设计

| 威胁 | 防护 |
|------|------|
| 恶意 JS 访问主文档 DOM | `sandbox="allow-scripts"` 阻止同源访问 |
| 窃取 localStorage | iframe 与主应用不同源，无法读取 |
| 加载恶意外部资源 | meta CSP 限制 `cdn.jsdelivr.net` 白名单 |
| postMessage 伪造 | 消息来源 `event.source === iframe.contentWindow` 校验 |

## 五、多 Agent 协作开发过程

本项目使用 Claude Code 的多 Agent 协作模式完成：

| Agent 角色 | 负责内容 |
|-----------|---------|
| dev-atoms-product-manager | PRD 撰写、用户故事拆解、功能优先级 |
| dev-atoms-frontend-developer | UI 实现（对话面板、预览面板、状态管理） |
| dev-atoms-backend-architect | 后端架构（Hono 路由、SQLite schema、SSE 代理） |
| dev-atoms-ai-engineer | LLM 集成（三阶段提示词、流式解析、降级逻辑） |
| dev-atoms-ux-designer | 交互设计、四态设计（加载/生成中/错误/空） |
| dev-atoms-reality-checker | 独立验证、PRD 覆盖率检查、E2E 自动化测试 |
| dev-atoms-data-engineer | 图表模板、数据导入导出 |

**验证铁律**：执行者 ≠ 验证者。每次功能完成后由 `reality-checker` 独立执行验收，证据存入 `evidence/` 目录。
